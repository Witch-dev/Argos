### 2026-09-30 — Writing feed card/modal: reviewer-pass fixes + live verification

A reviewer pass on `specs/writing-feed-card-and-modal.md` found two real bugs and one fragility, now fixed. (1) `WritingDetailModal.tsx`'s `startEditing()` and `updateMutation.onSuccess` didn't clear an active highlight-selection/region before/after an edit, which could let a stale selection submit a highlight-comment anchored to the wrong text in the newly-edited content — fixed by calling `annotations.cancelPendingSelection()`/`annotations.closeActiveRegion()` in both places. (2) `useAnnotatableText.ts` tracked the active highlighted region by a raw array index into a `regions` array that gets re-sorted on every highlights refetch — a race where a newly-landed highlight-comment could silently make the open panel point at the wrong region; fixed by keying the active region by its stable `[start,end)` span instead, re-derived (memoized) from the fresh `regions` array every render and self-closing if the span no longer matches anything — this fix lives in the shared hook, so `ReviewDetailPage`/`AnnotatableText` benefit too, not just the new modal. (3) `App.tsx`'s overlay-vs-full-screen routing decision relied solely on `location.state?.backgroundLocation`, which browsers persist across a hard reload of the same history entry — so refreshing while the overlay was open incorrectly kept rendering the overlay instead of the full-screen `WritingDetailModal` the spec requires; fixed with a new pure `wasHardReload()` helper (`lib/navigationReload.ts`, Navigation Timing API with a safe fallback) that detects a reload at mount and suppresses the stale `backgroundLocation` for that one load. Regression tests cover all three (`WritingDetailModal.test.tsx`, `AnnotatableText.test.tsx`, new `lib/navigationReload.test.ts`); full frontend suite 147 → 155, all passing, build and eslint clean on touched files (6 pre-existing unrelated lint errors elsewhere confirmed present on a clean baseline too, not introduced by this work). Separately, live-verified the data/API half of the feature against the real local dev Postgres (migrations already current): `sourceBookCoverUrl` resolution confirmed end-to-end for all three Writing shapes (Quote-with-book matches the book's real cover, Original-with-no-book leaves both cover fields null, Quote-with-typed-source leaves `sourceBookCoverUrl` null specifically because it's keyed off `SourceBookId` not `Kind` alone), and the highlight-comment API the right panel depends on (two overlapping highlight-comments merge into one region, voting updates score/ordering, `callerVoteValue` scoped per-caller) — no bugs found in this pass. Still open: an actual browser click-through of the modal's right-panel state machine and the full-screen-on-refresh fix — no browser-automation tool is available in this environment, so that remains a real, standing gap pending a manual pass. See `specs/writing-feed-card-and-modal.md`.

### 2026-09-30 — Writings & Annotations: review-pass fixes (real bug + 2 minor hardening)

Three fixes from a review pass on the comment/highlight system (`specs/writings-and-annotations.md`). (1) **Real bug**: `CommentService.GetTargetContentAsync` returned `null` for a `Review` target whenever `Log.ReviewText` was null/empty, which is indistinguishable from "the Log doesn't exist" — but `ReviewText` is mutable (`LogService.UpdateAsync` lets the author freely rewrite/clear it, unlike `Writing.Content`), so editing/clearing a review's text made `GET .../comments` and `.../highlights` falsely 404 even though the Log and its Comments were still alive. Fixed by replacing the collapsed `string?` return with a new `TargetContentLookup(bool Exists, string Content)` struct that distinguishes "target missing" from "target present but currently empty"; whole-post comments now correctly stay visible and highlight-comments correctly fall into the existing staleness path instead of 404ing. Added a regression test seeding a Log with a whole-post comment and a highlight-comment, clearing `ReviewText` via `LogService.UpdateAsync`, and confirming both reads still succeed. (2) **Vote race** (low-severity): `CommentService.VoteAsync` did read-then-write with no upsert, so two near-simultaneous identical votes could both pass the "no existing vote" check and the loser would throw an unhandled `DbUpdateException` (Postgres unique-violation, SqlState `23505`) as a 500. Wrapped the insert in a try/catch that treats that specific violation as a no-op (matches the pre-existing `catch (DbUpdateException)` retry pattern already used in `ListItemRepository`/`BookListService`, but scoped to the unique-violation case via `PostgresException.SqlState`). New test simulates the race via a `FakeCommentVoteRecordRepository.SimulateUniqueViolationOnNextAdd()` helper. (3) The `CK_Writings_KindSource` check constraint only constrained the `Quote` (`Kind = 1`) case, leaving `Original` (`Kind = 0`) rows free at the DB level to set `SourceBookId`/`SourceText` with nothing but the service layer stopping it. Tightened to require both directions in a new migration, `TightenWritingKindSourceConstraint` (`Argos.Infrastructure/Migrations/20260930231716_TightenWritingKindSourceConstraint.cs`), applied against the local Postgres; confirmed no existing `Writings` row violated the tightened constraint before or after. Full suite 157 → 159, all passing; `dotnet build` clean.

### 2026-09-28 — Fixed silent duplicate comments/replies/suggestions in Book Clubs

### 2026-09-28 — Fixed `confirm-book` 500 on bare-date checkpoints at the root (DateTime.Kind, not client workaround)

The frontend's live-verification pass found `POST /api/clubs/{id}/confirm-book` 500ing on a bare `"YYYY-MM-DD"` `DueDate` and worked around it client-side by always sending a full UTC ISO instant — real fix deferred to this pass. Root cause: ASP.NET's JSON model binder deserializes a date-only string into a `DateTime` with `Kind=Unspecified`, and Npgsql (no legacy-timestamp switch enabled) refuses to write `Kind=Unspecified` against a `timestamptz` column. No existing convention in `ArgosDbContext` handled this — every other `DateTime` in the app (`Log.StartedAt`/`FinishedAt`, `Post.CreatedAt`, etc.) is always server-set via `DateTime.UtcNow`, so `Kind` was already `Utc` and this never surfaced; `ReadingCheckpoint.DueDate` is the first client-supplied date in Argos. Fixed with a global EF Core value converter in `Apollon/src/Argos.Infrastructure/ArgosDbContext.cs` (`OnModelCreating`) applied to every `DateTime`/`DateTime?` property on every entity: `Unspecified` is treated as already-UTC (`DateTime.SpecifyKind(..., Utc)`), anything else is converted via `ToUniversalTime()` — a one-time fix at the DbContext layer rather than patching the one property, so any future client-supplied date field is covered automatically. No migration needed (provider-side conversion only, store type unchanged — confirmed by generating a probe migration and observing empty `Up`/`Down`, then removing it). Verified live: a real `POST /api/clubs/{id}/confirm-book` with `"dueDate":"2026-10-05"` (no time/timezone) now returns `200` and the checkpoint persists as `2026-10-05T00:00:00Z`. Full `dotnet test` suite: 92/92 still passing. The frontend's client-side workaround (`api/clubs.ts` sending `${date}T00:00:00.000Z`) is now redundant but harmless — left as-is since removing it isn't part of this backend fix.

### 2026-09-27 — Author names and a broken cover-id fallback fixed

User noticed Solaris showed no author and no cover on the book detail page. Two separate bugs: (1) `OpenLibraryClient` only ever mapped author *references* (`/authors/OL29655A`) from Open Library's work endpoint, never resolved them to actual names — a known, deliberately-deferred gap from `backend-tasks/05`. Fixed with `ResolveAuthorNamesAsync`, one follow-up HTTP call per author reference, applied in both `GetBookAsync` (new books) and `RefreshBookAsync` (the periodic refresh job). Fixed to skip non-positive ids. ### 2026-09-27 — Live Open Library search fallback

Book search previously only searched the local `Books` cache, which starts empty — searching for any book not already individually looked up (e.g. "solaris") returned "No books found" even though the book exists. Now search always also queries Open Library live, merges with cached results, and dedupes by Open Library ID. Live-only hits aren't persisted from search itself (Open Library's search endpoint doesn't return descriptions/subjects, only its per-book detail endpoint does) — caching with full detail still happens the existing way, the moment a book's detail page is opened. Zero frontend changes, zero migration. Full design and trade-offs: `specs/live-book-search.md`.
